# Архитектурные концепции: Bridge

В этом разделе объясняются ключевые проектные решения, которые обеспечивают стабильность и безопасность взаимодействия между веб-сервисами и Adobe Illustrator.

---

## 1. Механизм Watchdog и Concurrency Control

### Почему мост однопоточный?
Adobe Illustrator является **однопоточным десктопным приложением**. Его API (через COM-интерфейс) не поддерживает параллельное выполнение нескольких скриптов. Попытка отправить вторую команду, пока первая еще выполняется, приведет либо к ошибке COM, либо к непредсказуемому поведению интерфейса Illustrator.

### Реализация `is_busy`
Для предотвращения конфликтов в [main.py](/bridge/main.py) используется механизм блокировки:
1. **Глобальный Lock**: При получении запроса `/process` мост проверяет `busy_lock.locked()`.
2. **HTTP 429 (Too Many Requests)**: Если мост уже обрабатывает задачу, он немедленно возвращает статус 429. Это сигнализирует вызывающей стороне (например, n8n), что нужно подождать и повторить попытку позже.
3. **Background Task**: Сама обработка выполняется в фоновом режиме через `FastAPI BackgroundTasks`, чтобы не держать HTTP-соединение открытым слишком долго.

### Watchdog (Таймауты)
В [illustrator.py](/bridge/services/illustrator.py) реализован механизм `run_script_with_watchdog`. Если Illustrator зависнет (например, из-за модального окна или бесконечного цикла в скрипте), мост принудительно прервет выполнение по истечении `BRIDGE_JOB_TIMEOUT_SECONDS`, чтобы освободить ресурсы для следующих задач.

## 2. Механизм Handshake (Синхронизация файлов)

При работе в Docker-окружении используется общая папка (Shared Volume) между Linux (n8n) и Windows (Host с Illustrator).

### Проблема задержки
Файловые системы Docker (особенно на Windows через WSL2 или Hyper-V) могут иметь небольшую задержку при синхронизации файлов. Если n8n запишет файл `commands.json` и тут же вызовет API моста, мост на Windows может "не увидеть" файл в течение первых нескольких сотен миллисекунд.

### Решение: Handshake
В [workspace.py](/bridge/services/workspace.py) функция `wait_for_input` реализует цикл ожидания:
- Мост не запускает Illustrator, пока физически не обнаружит на диске все необходимые входные файлы (`commands.json` и исходный `.ai` файл).
- Это гарантирует, что к моменту старта скрипта все данные доступны. Если файлы не появятся в течение 30 секунд, мост вернет ошибку таймаута подготовки.

## 3. Безопасность

Мост выполняет произвольные скрипты в системе и имеет доступ к файловой системе хоста, поэтому защита критически важна.

### Авторизация `X-API-Key`
Все эндпоинты защищены зависимостью `verify_api_key` в [security.py](/bridge/utils/security.py). 
- **Зачем это нужно для n8n?** n8n обычно работает в облаке или другом контейнере. Если порт моста проброшен наружу, любой желающий может отправить вредоносный скрипт в Illustrator. 
- API-ключ гарантирует, что запросы приходят только от доверенного сервиса автоматизации.

### Защита от Path Traversal
В [workspace.py](/bridge/services/workspace.py) функция `validate_secure_path` проверяет каждый путь:
- Все операции должны происходить строго внутри разрешенной директории `exchange/jobs/`.
- Мост блокирует любые попытки выйти за пределы этой папки (например, через `../../windows/system32`). Это предотвращает несанкционированный доступ к системным файлам хоста через API моста.

## 4. Трансляция путей (Path Mapping)

Поскольку n8n работает внутри Docker (Linux), а Illustrator — на хост-машине (Windows), пути к файлам в запросах различаются. Мост автоматически выполняет трансляцию через функцию `normalize_path`.

### Схема маппинга
| Среда | Префикс пути | Пример пути к файлу |
| :--- | :--- | :--- |
| **n8n (Docker)** | `/data/exchange/` | `/data/exchange/jobs/{job_ID}/input/source.ai` |
| **Bridge (Windows)** | `C:\...\exchange\` | `C:\illustrator-automation\exchange\jobs\{job_ID}\input\source.ai` |

**Как это работает:**
- В `config.py` определена константа `DOCKER_PREFIX = "/data/exchange"`.
- При получении запроса мост ищет этот префикс, отсекает его и заменяет на локальный путь к папке `exchange` на диске Windows.
- Это позволяет n8n оперировать путями внутри контейнера, а Illustrator — работать с реальными файлами на диске.

## 5. Управление процессами и очистка "Зомби"-процессов

Adobe Illustrator может зависать или оставлять фоновые процессы при критических ошибках. Мост управляет жизненным циклом процесса `Illustrator.exe` через библиотеку `psutil`.

- **Очистка при старте**: При запуске моста (`on_startup`) вызывается метод `force_cleanup`, который находит и принудительно завершает все запущенные процессы Illustrator. Это гарантирует "чистый лист" для новых задач.
- **Watchdog Termination**: Если выполнение скрипта превышает `BRIDGE_JOB_TIMEOUT_SECONDS`, срабатывает Watchdog. Мост не просто возвращает ошибку, но и принудительно убивает процесс Illustrator, чтобы разблокировать COM-интерфейс и предотвратить накопление "зомби-процессов".
- **Метод очистки**: Сначала отправляется сигнал `terminate()`, и если процесс не закрылся за 5 секунд, применяется жесткий `kill()`.

## 6. Динамический Runner (runner.jsx)

Мост не вызывает основной скрипт автоматизации напрямую. Вместо этого он генерирует временный файл-посредник — **Runner**.

### Механика Динамического Раннера
Техническая необходимость использования Раннера обусловлена ограничениями Adobe Illustrator: метод `DoJavaScriptFile` (и COM-интерфейс в целом) не позволяет передавать аргументы напрямую в исполняемый скрипт. Файл-прослойка — единственный надежный способ передать контекст выполнения (`job_id`) внутрь среды ExtendScript.

**Логика работы:**
1. **Генерация**: Для каждого задания в папке `input/` создается уникальный файл `runner.jsx`.
2. **Передача контекста**: В файл записывается переменная `var CURRENT_JOB_ID = '...'`. Это единственный способ передать ID задания в среду ExtendScript, которая не имеет доступа к аргументам командной строки.
3. **Загрузка ядра**: Runner использует команду `$.evalFile()` для загрузки основного файла логики (`launch.js`).
4. **Исполнение**: Мост вызывает метод `DoJavaScriptFile` через COM-объект Illustrator, передавая путь к сгенерированному Runner-у.

После завершения задачи временный файл `runner.jsx` автоматически удаляется функцией `cleanup_job_workspace`.

## 7. Логика анализа логов (Log Analyzer)

После завершения работы скрипта в Illustrator, мост выполняет пост-обработку через [log_analyzer.py](/bridge/utils/log_analyzer.py). Это необходимо, так как метод `DoJavaScriptFile` может завершиться успешно на уровне COM, даже если внутри скрипта произошла логическая ошибка.

**Процесс анализа:**
1. **Поиск лога**: Мост сканирует папку `output/logs/` конкретного задания.
2. **Сканирование последних строк**: Анализатор считывает последние 10 строк самого свежего лог-файла.
3. **Ключевые слова**: Помимо общей метки `[ERROR]`, система ищет специфические маркеры:
   - `Font not found`: Проблемы с отсутствующими шрифтами в макете.
   - `Version mismatch`: Несоответствие версии файла и установленного Illustrator.
   - `Missing Link`: Отсутствие связанных изображений или ресурсов.
   - `Error opening file`: Файл поврежден или заблокирован.
4. **Влияние на ответ**: Если анализатор находит критическую ошибку, мост логирует детальное сообщение и может использовать его для уточнения причины сбоя в фоновой задаче, что помогает n8n быстрее диагностировать проблему через «умную» петлю ожидания.

## 8. Ограничения масштабируемости

При эксплуатации системы важно учитывать фундаментальное архитектурное ограничение:

**1 Экземпляр Моста = 1 Экземпляр Illustrator**

- **Однопоточность**: Из-за природы COM-интерфейса и самого Adobe Illustrator, один процесс Python не может эффективно управлять несколькими параллельными сессиями рисования.
- **Блокировка**: Именно поэтому в мосте реализован `busy_lock`. Попытка «распараллелить» задачи внутри одного инстанса приведет к конфликтам доступа к ресурсам графического движка и краху приложения.
- **SaaS-масштабирование**: Для увеличения пропускной способности системы (обработки множества задач одновременно) необходимо использовать горизонтальное масштабирование:
  - Развертывание дополнительных виртуальных машин (ВМ) с установленным Illustrator и Python Bridge.
  - Использование балансировщика задач на уровне n8n или внешнего брокера очередей.
  - Увеличение количества потоков в одном Python-процессе **не даст эффекта** и не является допустимым методом масштабирования данной архитектуры.
