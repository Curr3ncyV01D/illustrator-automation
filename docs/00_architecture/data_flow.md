# Потоки данных и взаимодействие сред

Обмен данными происходит между Логическим ядром (n8n) и Графическим ядром (Illustrator) через посредничество Моста.

Этот документ подробно описывает механизм обмена данными между изолированной средой n8n (Docker/Linux) и исполнительной средой Illustrator (Host/Windows) через общую директорию `exchange/`.

---

## 1. Механизм обмена через `exchange/`

Поскольку n8n работает внутри контейнера, а Illustrator — непосредственно в операционной системе Windows, прямой обмен данными между ними невозможен. Для решения этой задачи используется **Shared Volume** — общая папка, которая одновременно видна обеим системам.

### Маппинг путей (Path Mapping)

| Контекст | Базовый путь | Пример пути к входным данным |
| :--- | :--- | :--- |
| **Контейнер (n8n)** | `/data/exchange/` | `/data/exchange/jobs/{job_id}/input/commands.json` |
| **Хост (Windows)** | `C:\illustrator-automation\exchange\` | `C:\illustrator-automation\exchange\jobs\{job_id}\input\commands.json` |

Все пути в JSON-запросах от n8n приходят в формате Docker (`/data/...`). Мост автоматически транслирует их в локальные пути Windows перед передачей в Illustrator.

### Специфика Shared Volumes на Windows

Работа с общими томами (Shared Volumes) в Docker Desktop на Windows имеет архитектурную особенность:
- **Подсистема WSL2/Hyper-V**: Docker Desktop запускает легковесную виртуальную машину Linux (WSL2 или Hyper-V). Обмен файлами между этой ВМ и хостом Windows происходит через сетевой протокол (9P или gRPC FUSE).
- **Задержка синхронизации**: Из-за прослойки виртуализации изменения в файловой системе Linux (внутри контейнера n8n) не мгновенно отражаются в файловой системе Windows. Это может приводить к ситуациям "Race Condition", когда файл уже записан n8n, но еще не виден Мосту на хосте.

## 2. Механизм Handshake (Синхронизация)

Одной из критических проблем при работе с Docker Desktop на Windows является **задержка синхронизации файлов** (File Sync Latency) между виртуальной файловой системой Linux (WSL2/Hyper-V) и хост-машиной.

### Почему это важно?
Когда n8n скачивает файл в папку `/data/exchange/`, для Linux-процесса запись считается мгновенной. Однако физически на диске Windows файл может появиться с задержкой от 100мс до 2-3 секунд. Если Мост попытается запустить Illustrator сразу после получения HTTP-запроса, Illustrator выдаст ошибку "Файл не найден".

### Реализация Handshake
В [workspace.py](/bridge/services/workspace.py) реализована функция `wait_for_input`:
1. Мост получает запрос от n8n.
2. Вместо запуска скрипта, Мост входит в цикл ожидания (Polling).
3. Он проверяет физическое наличие файлов `commands.json` и исходного `.ai` на диске Windows.
4. Только после того, как **оба файла** обнаружены, Мост генерирует `runner.jsx` и передает управление Illustrator.

## 3. Трансляция и Инъекция путей (Context Injection)

Система использует стратегию **Context Injection**, при которой Мост (Python) выступает единственным источником истины о расположении файлов, диктуя их Графическому ядру (ExtendScript).

### Процесс трансляции
1. **n8n** отправляет запрос, содержащий Docker-путь к файлу (например, `/data/exchange/jobs/123/input/file.ai`).
2. **Мост** конвертирует этот путь в абсолютный Windows-путь (например, `C:\illustrator-automation\exchange\jobs\123\input\file.ai`).
3. **Мост** генерирует временный `runner.jsx`, в который записывает (инъектирует) абсолютные пути к коду (`CODE_ROOT`) и данным (`DATA_ROOT`).
4. **Ядро** принимает эти пути через метод `Config.init(codeRoot, dataRoot, jobId)`, настраивая всю внутреннюю логику работы с файлами.

### Таблица соответствия путей

| Сущность | Среда Docker (n8n) | Среда Host (Windows) | Среда JSX (Illustrator) |
| :--- | :--- | :--- | :--- |
| **Корень данных** | `/data/exchange/` | `C:\project\exchange\` | `C:/project/exchange` |
| **Корень кода** | — | `C:\project\src\` | `C:/project/src` |
| **Файл команд** | `/data/.../commands.json` | `C:\...\commands.json` | `C:/.../commands.json` |
| **Выходной PDF** | `/data/.../output/pdf/` | `C:\...\output\pdf\` | `C:/.../output/pdf/` |

*Примечание: В JSX путях всегда используются прямые слэши (`/`), что гарантирует корректную работу инструкций `#include` и объектов `File/Folder` в Illustrator под Windows.*

## 4. Жизненный цикл файлов (File Lifecycle)

Каждая задача проходит через строго определенные этапы работы с файлами:

1. **Скачивание (Download)**: n8n получает файлы из Telegram и сохраняет их в `/data/exchange/jobs/{job_id}/input/`.
2. **Валидация (Validation)**: n8n проверяет размер и тип файлов.
3. **Ожидание (Handshake)**: Мост дожидается появления файлов на диске Windows.
4. **Генерация Runner**: Мост создает временный `runner.jsx` в папке задания. На этом этапе происходит связка уникального `job_id` с кодом автоматизации: Мост инжектирует в файл глобальную переменную `var CURRENT_JOB_ID = "..."`, что позволяет Ядру корректно резолвить пути к входным данным и логам.
5. **Обработка (Processing)**: Illustrator читает файлы из `input/` и сохраняет результаты в `output/ai/` и `output/pdf/`.
6. **Доставка (Delivery)**: n8n обнаруживает готовые файлы в папке вывода и отправляет их пользователю.
7. **Очистка (Cleanup)**: 
   - Мост удаляет временный `runner.jsx` сразу после завершения скрипта.
   - n8n выполняет команду `rm -rf` для всей папки задания `{job_id}/` после успешной отправки или при возникновении критической ошибки.

---

## 4. Стратегия очистки и гигиены данных

Система использует многоуровневую стратегию для гарантии чистоты дискового пространства.

- **Штатная очистка**:
  - **Мост**: Удаляет временный `runner.jsx` сразу после завершения скрипта.
  - **n8n**: Выполняет рекурсивное удаление всей папки задания `exchange/jobs/{job_id}/` после успешной отправки результата пользователю или при возникновении штатной ошибки. Этот шаг выполняется в блоке `Finally` воркфлоу.

- **Очистка при сбоях**:
  - **Проблема**: Если сам воркфлоу n8n или Docker-контейнер аварийно завершает работу, папка задания может остаться на диске.
  - **Решение (в будущем)**: Для таких случаев планируется внедрение фонового **Cleanup Cron-скрипта**. Этот скрипт будет периодически (например, раз в час) сканировать директорию `exchange/jobs/` и удалять все папки задач, которые старше 24 часов, предотвращая накопление мусора.
