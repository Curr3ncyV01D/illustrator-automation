# Архитектурные концепции: n8n и Оркестрация

В этом разделе объясняются причины выбора тех или иных архитектурных решений для n8n в рамках проекта Illustrator Automation.

---

## 1. Manual Polling vs Webhooks

### Почему не Webhooks?
Обычно n8n использует **Webhooks** для получения сообщений в реальном времени. Однако это требует:
- Публичного IP-адреса.
- Настроенного SSL/HTTPS.
- Открытых портов в брандмауэре.

В корпоративных или локальных средах (где обычно запущен Adobe Illustrator) эти условия часто невыполнимы или ограничены системами DPI (Deep Packet Inspection), которые могут блокировать входящие соединения.

### Почему Polling (getUpdates)?
Мы выбрали **Manual Polling** (опрос через метод `getUpdates` в Telegram API):
1. **Надежность**: n8n сам инициирует исходящее соединение, которое гораздо реже блокируется сетевыми фильтрами.
2. **Локальность**: Система может работать на любом компьютере без сложной настройки сети.
3. **Контроль очереди**: Мы сами решаем, когда и сколько сообщений забирать, что критично для однопоточного Illustrator.

## 2. Механика Offset и предотвращение дублей

Для корректной работы Polling необходимо "запоминать", на каком сообщении мы остановились.

### Проблема "Бесконечного цикла"
Если n8n просто запрашивает сообщения без указания `offset`, Telegram будет возвращать одни и те же (уже обработанные) сообщения при каждом запросе. Это приведет к тому, что один и тот же файл будет генерироваться сотни раз.

### Решение: `latest_update_id + 1`
В воркфлоу реализована следующая логика:
1. n8n получает список сообщений.
2. Из последнего сообщения извлекается его `update_id`.
3. К этому числу прибавляется **1** (`latest_update_id + 1`).
4. Это значение сохраняется в файл [last_offset.txt](/exchange/last_offset.txt).
5. При следующем запросе n8n передает этот `offset` в Telegram, и сервер возвращает только **новые** сообщения, возникшие после этого ID.

## 3. Логика ожидания PDF и анализ логов

Процесс обработки в Illustrator может занимать от 10 секунд до нескольких минут. n8n должен понимать, когда работа завершена.

### Почему не "Wait 60 seconds"?
Простая пауза (Wait) — это ненадежное решение:
- Если задача выполнится за 10 секунд, мы теряем 50 секунд впустую.
- Если задача займет 70 секунд, n8n попытается забрать файл раньше времени и выдаст ошибку.

### Решение: Интеллектуальная петля (Loop)
Вместо фиксированной паузы n8n использует циклическую проверку (узел **Scanner Files**):
1. **Проверка файла**: n8n проверяет папку `output/pdf/` на наличие готового файла.
2. **Проверка ошибок**: Параллельно n8n считывает лог-файлы из `output/logs/`.
3. **Ранний выход (Early Exit)**: Если в логе обнаружена строка `[ERROR]`, n8n немедленно прерывает ожидание и отправляет уведомление об ошибке. Это экономит время пользователя и ресурсы системы.
4. **Таймаут**: Если по истечении общего лимита (например, 210 секунд) ни файл, ни ошибка не появились, система сообщает о таймауте.
